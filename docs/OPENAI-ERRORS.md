# OpenAI failure reporting and forced placements

The observed 49th turn on Oct 27, 2026 had exactly one legal placement. Its reconstructed canonical packet matches the stored request digest. The Decisions Choice contract requires 2–255 unique choices: https://developers.openai.com/api/reference/resources/decisions/methods/create. The old adapter sent that invalid one-choice request, then converted its provider rejection to `transport_ambiguous`. The old response status/message were not retained; the contract violation is confirmed, while the original provider's exact wording is unavailable. The failed turn took about174ms, below the1500ms decision deadline.

The browser service now resolves an independently rebuilt single-placement packet locally. It never pads the choice set, changes models or retries the old request. A `decision-browser-forced-receipt-1` records zero upstream attempts, zero provider completions, no observed model/usage, and zero API cost. Gravity still uses checked actual-state settlement before recording a placement. Paused mode still acknowledges commit. The canonical verifier accepts this receipt only when the original board has exactly one legal candidate. Truncating a multi-placement packet cannot obtain this path. Forced turns have a separate1000-entry aggregate bound in addition to existing game, recording, request and session limits.

Version2 browser accounting distinguishes real upstream completions from forced moves and retains the most recent safe diagnostic. Old accounting, receipts and records remain readable. Cost estimates count a validated forced move as zero rather than unknown usage. Provider details state the forced-move count; normal game layout is unchanged.

Failure entries retain HTTP status, an allowlisted provider error code, a bounded provider request ID, failure phase and elapsed time. A bounded, credential-redacted provider message and transport cause stay private in the owner ledger. Arbitrary provider text never reaches the browser or exported game record. HTTP rejections, service errors, connection failures and the actual decision deadline remain distinct. New errors retain the existing holds; no automatic retry, allowance refund or budget increase is added.

Recovery of the legacy rejected singleton requires explicit owner authority, a fully drained exited server, the exact ledger digest, a canonical matching one-choice packet and no other pending/uncertain requests. It preserves a backup and original entry, retires that lineage, retains billing uncertainty and carries all consumed attempts into the same-project/key successor. The original uncertainty-only recovery contract remains supported. This operation never claims a refund or replays the rejected choice.

Session expiry takes precedence over the per-decision deadline, so an activation ending during a request is reported as session expiry. Non-JSON HTTP errors retain their HTTP status; malformed HTTP200 success remains uncertain. A previous request diagnostic is used in the connection banner only when it matches the current hold reason, so stale refusals cannot hide a later acknowledgement problem.
